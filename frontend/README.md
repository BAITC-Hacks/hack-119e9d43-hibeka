# Фронтенд «Граф денег» — этап 1

Реализован пункт «Контракт и каркас» из фронтенд-ТЗ в переписке. Приложение
показывает адаптивный трёхпанельный экран, сводку и **синтетическую очередь только
для чтения**. Есть загрузка, успешный результат, пустой результат и ошибка.
Поиск, фильтры, выбор клиента, интерактивный граф, загрузка файлов и экспорт
ещё не подключены: соответствующие действия отключены с пояснением этапа.

## Запуск из корня репозитория

Нужен Node.js 22 (от 22.13) или 24+ и npm. Версии пакетов закреплены
в package.json и package-lock.json. Внешние ресурсы при просмотре не требуются.

```bash
npm --prefix frontend ci
npm --prefix frontend run dev
```

Адрес: http://127.0.0.1:5173. Для просмотра сборки:

```bash
npm --prefix frontend run build
npm --prefix frontend run preview
```

Стандартный адрес preview: http://127.0.0.1:4173.

## Данные и границы этапа

В проверенной копии проекта нет фронтенда, FastAPI, health endpoint,
дизайн-системы, макетов и AGENTS.md. Есть README, данные и Python starter.
Поэтому создан отдельный каталог frontend; Python-код и исходные Parquet не
менялись и не включаются в браузерную сборку.

Источник требований: приложенное «ТЗ разработки» v1.1 и уточняющее фронтенд-ТЗ,
раздел 21, «Этап 1 — контракт и каркас». Полный П0 общего ТЗ не равен первому
этапу фронтенда.

Существенные решения:

- React + TypeScript + Vite, обычный CSS, единые токены. Без UI-kit, роутера,
  глобального store и Cytoscape до этапа графа.
- Светлый интерфейс из ТЗ, системные локальные шрифты. Макетов не предоставлено.
- Очередь в каркасе — статическое представление ответа API; интерактивный выбор
  и полноценная карточка относятся к этапу 2.
- Начальные ответы целиком синтетические, включая 7 клиентов, суммы, роли,
  рейтинг и длительность расчёта. Они не получены из реального датасета.
- UI получает цифры из API-слоя, а не хранит их в компонентах. Формулы аналитики
  не реализованы на фронтенде.
- Только явный режим mock показывает примеры. http или неизвестный режим
  показывает ошибку о неподключённом API, без скрытого перехода к mock.
- Реального статуса сервера нет: health endpoint отсутствует в этой копии.
  Название и ответ endpoint нужно согласовать при интеграции.

## Проверка состояний

В верхней полосе «Демонстрационные данные» выбрать состояние:

| Состояние         | Ожидаемый результат                                        |
| ----------------- | ---------------------------------------------------------- |
| Готовый результат | Сводка и семь строк очереди после короткой задержки        |
| Загрузка          | Скелетоны и подпись, пока не выбран другой сценарий        |
| Нет данных        | Пояснение отсутствия готовых запусков; старые цифры убраны |
| Ошибка            | Понятная ошибка и кнопка повторной загрузки                |

Повтор в сценарии «Ошибка» намеренно повторяет ошибку; для моделирования
восстановления переключить на «Готовый результат». Повторная загрузка
отключена во время запроса. Переключение сценария отменяет предыдущий запрос;
запоздавшие ответы игнорируются. Переключатель сохраняет клавиатурный фокус.

Для задания начального состояния создать frontend/.env.local по примеру
.env.example и перезапустить Vite:

```text
VITE_API_MODE=mock
VITE_MOCK_SCENARIO=success
```

Допустимые сценарии: success, loading, empty, error. Неизвестный сценарий
использует success; неизвестный API-режим блокирует загрузку данных.

## Контракт для интеграции

- Типы находятся в src/types/api.ts. Все gid, id/source/target узлов графа и
  контрагенты — строки. Числовые gid отклоняются при загрузке очереди.
- Клиент первого этапа реализует только listRuns и listNodes; loadOverview
  выбирает последний завершённый запуск и проверяет единый run_id.
- Параметры фильтров закреплены в типах будущего контракта; mock первого этапа
  возвращает только начальную страницу и не реализует фильтрацию.
- listRuns пока возвращает Run[]. Вложенная структура RunSummary и поле
  priority_reason_short — предложенные формы для согласования с FastAPI,
  а не утверждение об уже существующем серверном контракте.
- Типы ClientDetails, GraphResponse, ClusterResponse фиксируют остальной
  контракт ТЗ; их методы и компоненты следующих этапов не реализованы.
- Nullable-метрики передаются как null. Кластеры в JSON используют top_gids:
  string[], в отличие от сериализованного JSON-поля внутри CSV.
- Будущий HTTP-адаптер подключается через src/api/index.ts. Компоненты не
  импортируют fixtures и не обращаются к fetch напрямую.
- Vite уже проксирует /api на http://127.0.0.1:8000. Сам HTTP-клиент, загрузка,
  polling и скачивание относятся к этапу 4.

## Проверки

```bash
npm --prefix frontend run typecheck
npm --prefix frontend run lint
npm --prefix frontend run format:check
npm --prefix frontend test
npm --prefix frontend run build
```

Тесты используют встроенный Node test runner и поддержку TypeScript Node 22.13+;
в версиях, где она экспериментальная, возможен ExperimentalWarning.
Отдельный test framework не установлен. ESLint проверяет TypeScript и правила
React Hooks, Prettier — форматирование.

Ручной сценарий: открыть все четыре состояния, повторить ошибку, восстановить
success, быстро переключить loading → empty → success; проверить точность gid,
отсутствие горизонтального переполнения на 375/768/1440 px и видимый Tab-фокус.
Skip-link переводит к main; подписи и состояния доступны скринридеру; анимации
отключаются при prefers-reduced-motion. Неактивные функции имеют пояснения.
