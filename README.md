# hack-119e9d43-hibeka
Hackathon team repository for HIBEKA

## Текущее состояние

Сервер FastAPI с проверкой доступности `GET /api/health`
и сводкой локальных данных `GET /api/data/summary` с проверкой их согласованности.
Направленный граф переводов строится с помощью NetworkX;
его сводка доступна через `GET /api/graph/summary`.
Показатели клиентов, включая PageRank и посредничество, доступны через
`GET /api/clients/metrics`.
Кластеры клиентов и их обороты доступны через `GET /api/clusters`.
Реализован полный расчёт признаков, шести ролей, рейтинга с объяснениями
и трёх обязательных CSV. Можно загрузить три файла через API и запустить
анализ в отдельном процессе. React-интерфейс подключён к API: очередь,
карточка, локальный граф, загрузка файлов и скачивание CSV.
Исходные данные находятся в `data/`, заготовка организаторов — в `starter/`.

## Полный анализ одной командой

После установки зависимостей из раздела ниже:

```bash
python run.py --data ./data --out ./out --config ./config.json
```

Результаты:

- `out/nodes_roles.csv` — каждый клиент, роль, сила признаков, кластер,
  приоритет и объяснение до 200 символов;
- `out/clusters.csv` — состав групп, внутренний оборот, до пяти главных
  клиентов и гипотеза о группе;
- `out/top_nodes.csv` — первые 50 клиентов с причинами приоритета.

Параметр `--top-n 20` меняет размер топа (минимум 20). Если клиентов меньше
запрошенного числа, выгружаются все и добавляется предупреждение.
CSV имеют UTF-8, разделитель запятую и точные десятичные gid. При открытии
в табличном редакторе импортируйте gid как **текст**.

Каждый запуск сохраняет снимок `out/runs/<run_id>/`: исходные файлы,
применённый `config.json`, CSV, `analysis.json`, `run_report.json`,
`role_diagnostics.json`, `ranking_review.md`, `ranking_sensitivity.json`.
Отчёт содержит SHA-256 входов/CSV/конфигурации, версии зависимостей,
длительность этапов, период данных, предупреждения и статус.
Повторный запуск сохраняет одинаковые CSV при одинаковых входах,
конфигурации, коде и среде; идентификатор и время запуска меняются.

`out/latest` — ссылка на последний успешный снимок; три CSV в корне `out`
ссылаются на него. Указатель переключается после проверки всех выгрузок.
При ошибке CLI возвращает код 1, сохраняет отчёт в `out/failed/` и не
подменяет предыдущий успешный результат. На macOS/Linux используется
атомарное переключение символической ссылки. Одновременный запуск в ту же
папку блокируется; после аварийного завершения перед удалением оставшейся
`.analysis.lock` нужно убедиться, что процесс расчёта завершён.

Методика: [docs/methodology.md](docs/methodology.md).
Разбор текущего топ-20: [docs/ranking_review.md](docs/ranking_review.md).
Ни роли, ни рейтинг не являются вероятностью виновности.

## Просмотр готового расчёта через API

После запуска CLI и сервера откройте `http://127.0.0.1:8000/api/runs`.
Из ответа возьмите `run_id`:

- `GET /api/runs/<run_id>` — отчёт и сводка;
- `GET /api/runs/<run_id>/nodes?limit=20` — очередь с глобальными рангами;
- `GET /api/runs/<run_id>/nodes/<gid>` — все признаки, объяснения и связи;
- `GET /api/runs/<run_id>/graph?gid=<gid>` — локальный граф выбранного клиента;
- `GET /api/runs/<run_id>/clusters` — группы с гипотезами и главными клиентами;
- `GET /api/runs/<run_id>/exports/nodes_roles.csv` — скачивание CSV
  (также разрешены `clusters.csv` и `top_nodes.csv`).

У очереди есть фильтры `role`, `cluster_id`, `is_seed`, `truncated_by_depth`,
`min_priority`, `offset`, `limit`. Фильтры не меняют глобальные оценки и ранги.
Экспорт возвращает заголовок `X-Run-Id`. Чтение готового снимка не запускает
аналитику заново. Для другой папки результатов задайте `GRAPH_OUTPUT_DIR`
перед запуском сервера. Форма загрузки и визуализация локального графа в React
относятся к следующему этапу.

### API локального графа

`GET /api/runs/<run_id>/graph?gid=<gid>&hops=1&limit=150` читает готовый
снимок без повторного расчёта аналитики. Обязательный `gid` передаётся полной
строкой, без преобразования в число JavaScript. Сейчас поддерживается один
шаг (`hops=1`): все непосредственные отправители и получатели.

Ответ содержит `run_id`, `gid`, `hops`, `limit`, `nodes`, `edges`,
`total_nodes`, `shown_nodes`, `truncated`. `total_nodes` — размер полного
окружения вместе с выбранным клиентом, до ограничения. Для подписи графа
используйте «Отображено shown_nodes из total_nodes узлов».

Лимит — от 1 до 150, по умолчанию 150. Выбранный клиент включается всегда
и стоит первым в `nodes`. Соседи выбираются по приоритету, округлённому до
12 знаков, по убыванию; при равенстве — по точному числовому gid. Глобальные
ранги, роли и оценки сохраняются. Изолированный клиент возвращается одним
узлом с пустым списком рёбер и `truncated=false`.

У узла есть строковые `id` и `gid`, роль, сила признаков, приоритет, глобальный
ранг, кластер, `depth`, `is_seed`, `is_isolated`, `truncated_by_depth`
и маркер `selected`. Фронтенд может использовать их для цвета и обозначений.
У ребра есть строковые `id`, `source`, `target`, сумма `sum_kzt` и число
операций `n_tx`. `id` составлен как `src->dst`: встречные переводы различаются.

Выбор соседей учитывает оба направления, а рёбра сохраняют исходное направление.
В ответ входят все связи между показанными узлами, включая связи между соседями.
Ограничение графа не урезает полные таблицы контрагентов в карточке клиента.
Неизвестный клиент/запуск получает 404, неготовый результат — 409,
некорректные `hops`/`limit` или отсутствующий `gid` — 422.

## Загрузка файлов и фоновый расчёт

Сначала запустите сервер по инструкции ниже. Из корня проекта можно отправить
предоставленные данные:

```bash
curl -X POST http://127.0.0.1:8000/api/runs \
  -F 'nodes=@data/nodes.parquet' \
  -F 'edges=@data/edges.parquet' \
  -F 'transactions=@data/transactions.parquet'
```

Все три multipart-поля обязательны. Имена загруженных файлов не используются
как пути: файлы сохраняются во внутреннюю папку с фиксированными именами.
Лимит одного сохраняемого файла — 128 MiB. Используется текущая серверная
`config.json`; её копия закрепляется за запуском.

После приёма файлов сервер возвращает HTTP 202:

```json
{"run_id": "<идентификатор запуска>", "status": "queued"}
```

Для состояния расчёта опрашивайте `GET /api/runs/<run_id>` раз в 1–2 секунды.
Остановите опрос при `completed` или `failed`:

- `queued` — файлы приняты, процесс готовится к запуску;
- `running` — выполняется расчёт; `stage` содержит текущий этап;
- `completed` — готовы сводка и CSV, доступны очередь, карточки и кластеры;
- `failed` — расчёт не выполнен; причина находится в `error.message`.

Этапы: `starting`, `copying_inputs`, `validation`, `graph_and_clusters`,
`features`, `roles_and_ranking`, `diagnostics`, `exports`, `publishing`.
Состояние содержит `run_id`, `status`, `stage`, `summary`, `warnings`, `error`.
При ошибке сохраняется `failed_stage`. `GET /api/runs` показывает успешные,
ожидающие, выполняющиеся и неудачные API-запуски, а также готовые CLI-запуски.

Аналитика выполняется в отдельном Python-процессе через тот же pipeline, что
CLI. FastAPI продолжает отвечать на чтение статуса и готовых результатов.
Один слот расчёта на папку `GRAPH_OUTPUT_DIR` общий для API и CLI и резервируется
до сохранения файлов. Повторный запуск при занятом слоте получает HTTP 409.
Неудачный новый запуск не подменяет предыдущий успешный снимок или его CSV.

Коды ответов:

- 202 — загрузка принята, `run_id` выдан;
- 422 — отсутствует обязательное поле или запрос некорректен;
- 413 — файл превышает лимит;
- 409 — слот занят либо запрошены результаты ещё неуспешного запуска;
- 404 — неизвестный запуск/клиент/файл выгрузки;
- 503 — не удалось сохранить загрузку или подготовить конфигурацию.

Ошибки содержимого Parquet появляются асинхронно как `status=failed`,
`error={code,message,details}`. HTTP-ошибки загрузки/состояния используют такую
же структуру в `detail`. Логи рабочего процесса находятся во внутренней
папке `out/jobs/<run_id>/worker.log`; через exports доступны только три CSV.
Временные загрузки удаляются после завершения процесса; исходный снимок
успешного расчёта хранится в `out/runs/<run_id>/inputs`.

Штатная остановка сервера ожидает фоновые задачи. После принудительного
завершения сервера/компьютера задача может остаться с незавершённым статусом
и блокировкой: автоматическое возобновление пока не реализовано. Перед
очисткой блокировки убедитесь, что сервер и рабочий процесс завершены,
сохраните диагностику и отправьте файлы новым запуском.

Описанные ниже `/api/data/summary`, `/api/graph/summary`, `/api/clients/metrics`
и `/api/clusters` — диагностические методы текущей папки `data/`.
Они пересчитывают данные при запросе и не заменяют API готового запуска.

## Установка

Команды выполняются из корня репозитория. Нужен Python 3.12 или новее;
проверено на Python 3.12.14 и 3.14.4. Системный Python 3.9 не подходит.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Если установлена более новая версия Python, укажите её исполняемый файл вместо
`python3.12`. При существующем корректном окружении достаточно его активировать.

## Сводка данных

```bash
curl http://127.0.0.1:8000/api/data/summary
```

Ответ для предоставленного датасета:

```json
{
  "nodes_count": 2248,
  "edges_count": 3119,
  "transactions_count": 4840,
  "total_amount_kzt": 365890012.01,
  "validation": {
    "status": "passed",
    "warnings": [
      "Изолированных клиентов: 19. Они сохранены в сводке.",
      "Повторяющихся строк операций: 97. Они сохранены; transaction_id отсутствует.",
      "Клиентов на depth=4 без исходящих: 444. Продолжение потока не наблюдается.",
      "Исходных клиентов seed: 81. Их входящие потоки могут быть неполными.",
      "Клиентов с исходящей суммой больше наблюдаемой входящей: 377. Полный баланс неизвестен."
    ]
  }
}
```

Количество клиентов берётся из `nodes.parquet`, включая изолированных,
связей — из `edges.parquet`, операций — из `transactions.parquet`.
Общая сумма рассчитывается только по операциям из `transactions.parquet`.
Совпадающие строки операций сохраняются. Каждая сумма переводится в целые
тиыны через десятичную арифметику с округлением ROUND_HALF_UP до двух знаков.
Сложение и сравнение выполняются в тиынах; API возвращает итог в KZT.

Папка `data/` определяется относительно проекта, независимо от текущей
рабочей папки процесса. Файлы читаются при каждом запросе, без кэша.

## Проверка согласованности

Перед выдачей сводки проверяются:

- все обязательные столбцы, их типы и отсутствие пропущенных значений;
- идентификаторы `gid`, `src`, `dst` строго типа int64, без преобразования в float;
- уникальность клиентов и направленных пар в `edges`;
- наличие всех отправителей и получателей в `nodes`;
- конечные положительные суммы и целое положительное `n_tx`;
- диапазоны `depth` и соответствие `is_seed` глубине 0;
- корректный тип календарных дат;
- совпадение наборов пар, количества операций и сумм между `edges` и `transactions`.

Сумма каждой пары сравнивается с абсолютным допуском 0,01 KZT независимо
от величины суммы. В случае расхождения сервер указывает пару и значения
из обоих источников. Число клиентов не зашито в проверки.

Если файл отсутствует, повреждён или проверка не пройдена, сервер возвращает
HTTP 503 с первой обнаруженной причиной в поле `detail`. Успешная сводка
содержит `validation.status = "passed"` и список предупреждений.

Изоляты, одинаковые строки операций, граница четвёртого колена и неполные
потоки не блокируют расчёт. Операции меньше 5 000 KZT или вне июля 2026
отмечаются как отклонения от профиля текущего кейса и также не блокируют
сводку, если сами файлы согласованы. Исходные файлы не изменяются.

## Граф переводов

```bash
curl http://127.0.0.1:8000/api/graph/summary
```

Ответ для предоставленного датасета:

```json
{
  "directed": true,
  "nodes_count": 2248,
  "edges_count": 3119,
  "seed_count": 81,
  "isolated_nodes_count": 19,
  "weak_components_count": 35,
  "largest_component_size": 1877
}
```

Граф строится в памяти после проверки всех трёх файлов и пересоздаётся при
каждом запросе. Сначала добавляются все клиенты, включая изолированных.
Узлы сохраняют точные целочисленные идентификаторы, `depth` и `is_seed`.
Каждая строка `edges.parquet` становится направленной связью отправитель →
получатель с атрибутами `sum_kzt`, `n_tx` и `depth`. Встречные переводы
сохраняются как отдельные связи.

`weak_components_count` — число отдельных частей графа, если не учитывать
направление связей: 16 частей со связями и 19 одиночных клиентов.
Это компоненты связности, а не результат кластеризации. Крупнейшая часть
содержит 1 877 клиентов. Этот endpoint возвращает только сводку;
визуализация и определение ролей будут добавлены следующими этапами.
Ошибки чтения или проверки данных возвращаются с HTTP 503 и полем `detail`.

## Показатели клиентов

`GET /api/clients/metrics?offset=0&limit=100` возвращает `total_count`,
`offset`, `limit`, список `items` и результат проверки данных `validation`.
По умолчанию выдаются первые 100 клиентов, максимум — 500 за запрос.
Следующая страница: `offset=100&limit=100`. Клиенты отсортированы по числовому
`gid`; смещение за концом списка возвращает пустой `items`.
Некорректные параметры возвращают HTTP 422, ошибки данных — HTTP 503.

Каждая запись содержит:

| Поле | Значение |
|---|---|
| `gid` | Идентификатор строкой, без потери точности в JavaScript |
| `cluster_id` | Номер сообщества клиента в полном графе |
| `depth`, `is_seed` | Исходные признаки клиента |
| `is_isolated` | Нет входящих и исходящих связей |
| `in_deg`, `out_deg` | Число различных отправителей и получателей соответственно |
| `in_tx`, `out_tx` | Число входящих и исходящих операций: сумма `n_tx` связей |
| `in_kzt`, `out_kzt` | Суммы входящих и исходящих связей в KZT |
| `net_flow_kzt` | `in_kzt - out_kzt`: наблюдаемый чистый поток, не остаток на счёте |
| `pagerank` | PageRank направленного графа с весами по суммам переводов |
| `betweenness` | Нормализованное посредничество по направленным кратчайшим путям |

Расчёт охватывает всех клиентов, включая изолированных с нулевыми суммами,
числом связей и операций. Встречный контрагент учитывается в каждом направлении отдельно.
Суммы берутся из связей графа (`edges.parquet`), округляются до тиынов
по правилам проверки данных и складываются целыми числами. API выдаёт суммы
числами в KZT. Операции с одинаковыми строками остаются учтены в `n_tx`.
Все показатели относятся только к наблюдаемым переводам; входящие потоки
и продолжение за четвёртым коленом могут быть неполными.
При каждом запросе файлы проверяются, граф и показатели пересчитываются.

### Положение клиента в графе

PageRank рассчитывается с `alpha=0.85`, `max_iter=1000`, `tol=1e-8`,
равномерной персонализацией и весом `sum_kzt`. Вес определяет относительную
долю каждой исходящей связи отправителя. Для узлов без исходящих связей
используется равномерное распределение. Изолированные клиенты сохраняют
базовый положительный PageRank; он не означает наличие переводов.
Если алгоритм не сошёлся, API возвращает HTTP 503 с объяснением в `detail`,
а не подставляет нулевые значения.

Посредничество рассчитывается точно (`k=None`), с нормализацией,
по направленному графу без весов расстояния (`weight=None`). Концы пути
не считаются посредниками (`endpoints=False`). Метрика отражает участие
узла в структурных кратчайших путях, а не долю денег, прошедших через него.
У изолированных клиентов посредничество равно нулю.

Обе метрики рассчитываются по полному графу до разбиения на страницы.
Параметры `offset` и `limit` не меняют значения метрик. Порядок клиентов
по-прежнему определяется `gid`; роли и рейтинг доступны в API готового запуска.
Высокое значение этих показателей само по себе не доказывает мошенничество.

## Кластеры клиентов

`GET /api/clusters?offset=0&limit=100` возвращает `total_count`, `offset`,
`limit`, список `items` и `validation`. Максимум — 500 кластеров за запрос.
Каждая запись содержит:

| Поле | Значение |
|---|---|
| `cluster_id` | Номер кластера от 0 |
| `n_nodes` | Число клиентов |
| `n_seed` | Число исходных клиентов |
| `internal_kzt` | Сумма направленных переводов внутри кластера |
| `incoming_kzt` | Сумма переводов из других кластеров |
| `outgoing_kzt` | Сумма переводов в другие кластеры |

Для Louvain строится отдельный неориентированный граф: встречные суммы
складываются. Веса хранятся в целых тиынах; одинаковое масштабирование
всех сумм сохраняет их относительные веса. Используются `resolution=1`
и `seed=42`, узлы и связи предварительно сортируются по точным gid.
Исходный направленный граф сохраняется.

Кластеры нумеруются по убыванию размера, при равенстве — по минимальному gid.
Изолированные клиенты входят каждый в собственный кластер. Для пустого
графа список пустой; при отсутствии ненулевых весов каждый клиент образует
отдельный кластер. Проверяется, что каждый клиент включён ровно один раз.

Обороты считаются по исходным направленным связям: каждая связь учитывается
один раз во внутреннем обороте либо как исходящая у одной группы и входящая
у другой. Внутренний оборот — сумма переводов, а не объём уникальных денег.
Сумма `internal_kzt + outgoing_kzt` по всем группам равна сумме связей графа.

`cluster_id` в показателях клиентов и сводке кластеров относится к одному
расчёту при одинаковых данных и версиях библиотек. Пагинация не меняет
группы. При изменении данных номера могут измениться.
Кластеры описывают структуру переводов и не доказывают преступную деятельность.
Главные клиенты, роли и гипотезы доступны в `/api/runs/<run_id>/clusters`.
Диагностический `/api/clusters` пересчитывает только базовую сводку.

## Проверка реализации

После активации виртуального окружения:

```bash
python -m unittest discover -s backend/tests -v
```

Проверки используют небольшие искусственные таблицы и временные файлы;
предоставленный датасет не редактируется.
HTTP-проверки загрузки поднимают временный сервер на свободном локальном
порту и запускают реальные рабочие процессы. Результаты пишутся во временную
папку, отдельно от `out/`. Проверяются успешная загрузка, совпадение CSV с CLI,
статусы, занятый слот, повреждённые данные, отмена загрузки и сбои процесса.

## Фронтенд

React + TypeScript + Cytoscape: очередь проверки, поиск и фильтры, карточка клиента,
локальный граф, загрузка данных и скачивание трёх CSV. Интерфейс работает с FastAPI.
Требуется Node.js 22 (от 22.13) или 24+.

При запущенном бэкенде на порту 8000:

```bash
npm --prefix frontend ci
npm --prefix frontend run dev
```

Откройте http://127.0.0.1:5173. Подробности — в [frontend/README.md](frontend/README.md).
